
# Keychron Q4 Pro: исправление зависания и чёрного экрана при переключении TTY #

## Окружение ##

- **ОС:** Arch Linux, X11 (`startx` с `tty1`), Openbox;

- **Клавиатура:** Keychron Q4 Pro, USB VID:PID `3434:0640`, прошивка QMK/VIA;

- **Видеокарта:** NVIDIA RTX A2000 12 GB; во время диагностики — драйвер `nvidia-open-dkms`/`nvidia-utils` версии `620.70.06`;

- **Ядро при диагностике:** `linux-lts 6.18.63-3`;

- **Композитор:** `picom v13`, backend `glx`;

- **Переключение консолей:** слой клавиатуры с F1–F12, а также команда `chvt`.

## Симптомы ##

1. При переходе с графической сессии на другой TTY и попытке возврата на `tty1`
   машина переставала реагировать на локальный ввод; проблема воспроизводилась и
   через `chvt 1`, поэтому не была связана только с горячими клавишами QMK;

2. После устранения первого сбоя обнаружилась другая проблема: при возврате на
   `tty1` показывался чёрный экран. При этом Xorg и Openbox оставались
   запущенными. Завершение `picom` из другого TTY восстанавливало изображение, а
   повторный запуск `picom` возвращал композитинг.

## Исправление 1: ошибочная классификация HID-интерфейса Keychron ##

В журнале Xorg интерфейс `Keychron Q4 Pro System Control` (`/dev/input/event10`
на момент диагностики) был отмечен как `Keyboard Joystick`.

Проверка свойств устройства:

```sh
udevadm info --query=property --name=/dev/input/event10 | grep '^ID_INPUT'
```

До исправления вывод содержал `ID_INPUT_JOYSTICK=1`.

### Шаг 1. Создать локальное правило hwdb ###

Файл `/etc/udev/hwdb.d/61-input-id-local.hwdb`:

```ini
id-input:modalias:input:*v3434p0640*
  ID_INPUT_JOYSTICK=
```

**Важно:** перед `ID_INPUT_JOYSTICK` должен быть пробел; значение оставлено
**пустым**, не `0`. В данной системе `ID_INPUT_JOYSTICK=0` привело к изменению
значения свойства, но зависание сохранилось. После удаления свойства с помощью
пустого значения зависания прекратились. Это наблюдение относится к описанной
конфигурации; не следует считать его универсальным для всех версий udev.

Идентификатор устройства ввода можно получить следующим образом.

```
cat /sys/class/input/event10/device/modalias
```

После выполнения мы получим следующий вывод:

```
input:b0003v3434p0640e0111-e0,1,3,4,k74,8A,8B,8E,8F,94,AE,E3,F8,161,164,198,1B6,24E,24F,ra10,11,28,m4,lsfw
```

### Шаг 2. Обновить базу и повторно обработать устройство ###

Из-под пользователя `root` выполнить следующую команду:

```sh
systemd-hwdb update
udevadm trigger --action=change /dev/input/event10
udevadm settle
```

**Важно:** `systemd-hwdb update` перестраивает базу, но сам по себе не применяет
изменения к уже обнаруженному устройству. Команда `trigger` инициирует повторную
обработку, а `settle` ожидает окончания очереди событий. Номер `/dev/input/event10`
может измениться после перезагрузки; перед выполнением необходимо найти актуальный
узел для `Keychron Q4 Pro System Control`.

Узнать соответствующий путь можно, например, так:

```sh
for e in /sys/class/input/event*
do
  if grep -q 'Keychron Q4 Pro System Control' "$e/device/name" 2>/dev/null
  then
    printf '/dev/input/%s\n' "${e##*/}"
  fi
done
```

### Шаг 3. Проверить свойства ###

```sh
udevadm info --query=property --name=/dev/input/event10 | grep '^ID_INPUT'
```

Успешный результат (в описанном случае):

```text
ID_INPUT=1
ID_INPUT_KEY=1
```

Строки `ID_INPUT_JOYSTICK` больше нет. После перезапуска X11 в актуальном
`~/.local/share/xorg/Xorg.0.log` устройство отмечается только как `Keyboard`,
без `Joystick`.

Для проверки совпадения hwdb можно использовать фактический modalias:

```sh
cat /sys/class/input/event10/device/modalias
systemd-hwdb query "id-input:modalias:$(cat /sys/class/input/event10/device/modalias)"
```

## Исправление 2: чёрный экран из-за picom при возврате в X11 ##

Условия: `picom v13`, `backend = "glx"`, `vsync = true`, `use-damage = true`, NVIDIA.

Когда чёрный экран возникал, команда на другом TTY:

```sh
pkill -TERM -x picom
```

восстанавливала рабочий стол. Это подтвердило непосредственную связь с композитором.

### Исправление ###

В файл `~/.config/picom/picom.conf` добавить или включить параметр:

```ini
xrender-sync-fence = true;
```

Остальные настройки, включая `backend = "glx"`, менять не потребовалось.

Перезапуск композитора:

```sh
pkill -TERM -x picom
picom --daemon
```

**Проверка:** многократные переходы с `tty1` на другие TTY и обратно, в том
числе после перезапуска `picom` и после перезагрузки компьютера. В проведённых
тестах чёрный экран перестал возникать. Это подтверждённое практическое
исправление для данной системы, а не гарантия отсутствия проблемы во всех
конфигурациях.

## Итоговая проверка ##

1. Убедиться, что у Keychron System Control **отсутствует** `ID_INPUT_JOYSTICK`;

2. Убедиться, что в конфигурации `picom` есть `xrender-sync-fence = true;` и композитор перезапущен;

3. Запустить X11 через `startx` на `tty1`;

4. Перейти на `tty2` и вернуться командой `sudo chvt 1` либо сочетанием клавиш;

5. Повторить несколько раз, в том числе после перезагрузки.

## Откат ##

**hwdb:** удалить локальную запись из `/etc/udev/hwdb.d/61-input-id-local.hwdb`
(или сам файл, если он содержит только это правило), затем выполнить:

```sh
sudo systemd-hwdb update
sudo udevadm trigger --action=change /dev/input/event10
sudo udevadm settle
```

Уточнить номер event-узла перед выполнением и перезапустить X11. **Внимание:**
откат может вернуть первоначальное зависание.

**picom:** убрать `xrender-sync-fence = true;` и перезапустить композитор.

**Внимание:** откат может вернуть чёрный экран.

## Дополнительные замечания ##

- Актуальный журнал пользовательского Xorg находился в
  `~/.local/share/xorg/Xorg.0.log`. Файл `/var/log/Xorg.0.log`, показанный в
  ходе диагностики, был старым (от февраля 2026 года) и не относился к текущему
  запуску;

- Параметры `nvidia_drm` при проверке: `modeset=Y`, `fbdev=Y`. Изменять их для
  решения этих проблем не понадобилось;

- Предыдущие аварийные перезагрузки могли оставлять файлы блокировки
  `~/.Xauthority-*`, влияющие на последующий запуск `startx`; это отдельная
  возможная проблема, а не установленная причина описанных сбоев.
